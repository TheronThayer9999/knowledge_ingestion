# Refresh token — thiết kế B (rotation + reuse detection)

Trạng thái: **đã triển khai P0 (22/10/2026)**. Tài liệu này giải thích vì sao cần,
thiết kế hoạt động thế nào, và phần nào cố ý để lại cho giai đoạn sau.

---

## 1. Vì sao cần — giải thích từ đầu (không cần biết trước về OAuth)

### 1.1. Hiện trạng trước khi sửa: một chiếc "vé" sống 24 giờ

Hệ thống đang phát một JWT duy nhất. Hãy hình dung nó là **vé vào cổng**:

- Server ký vé, client cầm vé, mỗi request trình vé. Server chỉ kiểm tra **chữ ký + hạn**,
  không giữ danh sách vé đã phát.
- Vé sống **1440 phút = 24 giờ** (`jwt.expiry_minutes`).

Hệ quả — đây là 3 vấn đề thật, không phải lý thuyết:

1. **Logout không có tác dụng phía server.** Client xoá vé khỏi trình duyệt, nhưng nếu ai đó
   đã copy vé (XSS, máy bị chiếm, log lộ), họ vẫn vào được đến khi vé hết hạn. Server không có
   cách nào "huỷ vé số 123" vì nó không biết vé nào đang tồn tại.
2. **Vé sống quá lâu.** Một vé bị lộ là 24 giờ truy cập trái phép.
3. **Thu hồi chỉ ở mức "tất cả hoặc không gì".** Đổi mật khẩu sẽ đá mọi token (nhờ so
   `password_changed_at` với DB mỗi request), nhưng không thể đá **một thiết bị** trong khi
   các thiết bị khác vẫn đăng nhập.

> Chi tiết dễ bỏ qua: middleware hiện **query DB mỗi request** để lấy user và so
> `password_changed_at`. Nghĩa là JWT ở đây đã không còn "stateless" như quảng cáo —
> server đã có state, chỉ là state đó chưa dùng để quản lý phiên.

### 1.2. Refresh token giải quyết bằng cách tách làm hai loại vé

Hãy hình dung một cơ chế thẻ ra vào:

| | Access token (vé ngắn) | Refresh token (thẻ dài) |
|---|---|---|
| Hạn | ngắn (mục tiêu 15 phút) | dài (30 ngày) |
| Dùng để | gọi API | **đổi lấy vé ngắn mới** |
| Client gửi kèm | mọi request | chỉ khi gọi `/auth/refresh` |
| Server lưu | không | **có — chỉ lưu hash** |
| Thu hồi được | không (chờ hết hạn) | **có, ngay lập tức** |

Lợi ích:

- Vé bị lộ chỉ dùng được tối đa 15 phút thay vì 24 giờ.
- Thẻ dài nằm trong DB nên logout/đổi pass/khoá tài khoản **thu hồi được thật**.
- User không phải đăng nhập lại mỗi ngày: thẻ tự đổi vé mới.

### 1.3. Vì sao phải "rotation" — mỗi thẻ chỉ dùng một lần

Nếu thẻ 30 ngày được dùng lại nhiều lần, kẻ trộm copy thẻ sẽ dùng song song với user mà không
ai biết. Rotation đổi luật:

- Mỗi lần refresh, thẻ cũ bị đánh dấu **đã dùng** (`rotated_at`) và server phát thẻ mới.
- Thẻ mới thuộc cùng **family** (cùng một lần đăng nhập / một thiết bị).
- Nếu một thẻ **đã dùng** lại xuất hiện → chắc chắn có **hai bản sao**. Đây là dấu hiệu bị đánh cắp.

### 1.4. Vì sao phát hiện dùng lại thì phải "thu hồi cả family"

Khi thấy thẻ đã dùng xuất hiện lần nữa, server **không biết ai là kẻ trộm**: cả user thật và kẻ
trộm đều có thể là người đang gửi. Có hai lựa chọn:

- **Bỏ qua** → kẻ trộm giữ quyền truy cập vô thời hạn. Không chấp nhận được.
- **Thu hồi cả family** → cả hai bị đăng xuất; user thật phiền một lần, kẻ trộm mất quyền ngay.

Chọn cách thứ hai. Đây là đánh đổi có chủ ý: **an toàn thắng tiện lợi** khi có dấu hiệu bất thường.
Log sẽ ghi `user_id`, `family_id`, IP để điều tra.

### 1.5. Vì sao không lưu token gốc trong DB

Token gốc chỉ được trả về client **đúng một lần**. DB chỉ lưu `SHA-256(token)`:

- DB bị đọc (backup lộ, SQL injection, nhân viên tò mò) → kẻ tấn công chỉ thấy hash,
  không thể dùng hash để gọi API (server băm cái client gửi rồi so hash).
- Token có 256 bit entropy ngẫu nhiên nên không cần bcrypt/argon2 (những hàm đó dành cho
  mật khẩu entropy thấp); SHA-256 là đủ và tra cứu được bằng unique index.

### 1.6. Trước và sau — bảng so sánh

| Tình huống | Trước | Sau |
|---|---|---|
| Token bị lộ | Dùng được tới 24 giờ | Access ngắn (mục tiêu 15 phút); refresh dùng 1 lần, dùng lại là mất cả phiên |
| Logout | Client tự xoá, server không biết | Server thu hồi refresh token, không đổi được vé mới |
| Đổi mật khẩu | Đá mọi access token | Đá mọi access **và** mọi refresh token |
| Khoá tài khoản | Chặn request mới | Chặn + thu hồi toàn bộ refresh token |
| Đăng nhập nhiều thiết bị | Không phân biệt | Mỗi lần login một family riêng; logout 1 thiết bị không ảnh hưởng thiết bị khác |
| Xem/ thu hồi thiết bị | Không thể | Có dữ liệu UA/IP; UI là việc của P1 |

## 2. Thiết kế B hoạt động thế nào

> Luồng chi tiết từng bước — sequence diagram, trạng thái DB sau mỗi bước, ma trận lỗi,
> đua 2 tab và ví dụ curl — nằm ở `technical_debt/AUTH_REFRESH_TOKEN_FLOW.md`.

### 2.1. Bảng `refresh_tokens`

```sql
CREATE TABLE refresh_tokens (
  id                bigint generated by default as identity PRIMARY KEY,
  user_id           bigint      NOT NULL,
  family_id         uuid        NOT NULL,      -- 1 lần login = 1 family
  token_hash        char(64)    NOT NULL UNIQUE, -- hex(SHA-256(token))
  expires_at        timestamptz NOT NULL,      -- hạn của riêng token này
  family_expires_at timestamptz NOT NULL,      -- hạn tuyệt đối của cả phiên
  rotated_at        timestamptz,               -- != NULL: đã dùng 1 lần
  revoked_at        timestamptz,               -- != NULL: bị thu hồi
  revoke_reason     varchar(32),               -- logout | reuse_detected | password_changed | admin
  user_agent        varchar(255),
  ip                varchar(64),
  created_at        timestamptz,
  updated_at        timestamptz,
  deleted_at        timestamptz
);
```

GORM tự tạo bảng qua `AutoMigrate` (đã thêm `domain.RefreshToken{}` vào `migrate.go`);
không cần migration tay.

- `family_expires_at` chặn trường hợp token bị đánh cắp "sống mãi" nhờ refresh liên tục:
  quá 90 ngày kể từ lần login đầu, family chết dù token lẻ còn hạn.
- `user_agent`/`ip` chỉ để audit và làm UI thiết bị sau này.

### 2.2. Đăng nhập

```
POST /auth/login
  → verify bcrypt như cũ
  → sinh family_id (UUIDv7) + refresh token ngẫu nhiên 32 byte
  → INSERT refresh_tokens(hash, family_id, expires = now+30d, family_expires = now+90d)
  → ký access JWT (hạn 24h hiện tại, sẽ hạ 15m sau khi FE xong)
  → trả { token, expires_at, refresh_token, refresh_expires_at, user }
```

Mỗi lần login (kể cả cùng user trên thiết bị khác) tạo family mới. Đăng xuất thiết bị này
không đá thiết bị kia.

### 2.3. Đổi vé

```
POST /auth/refresh { refresh_token }
  BEGIN
    SELECT ... FROM refresh_tokens WHERE token_hash = ? FOR UPDATE
    không thấy / hết hạn / family hết hạn / đã thu hồi → 401 (cùng một message)
    rotated_at != NULL                                 → REUSE → thu hồi cả family → 401
    UPDATE dòng cũ: rotated_at = now
    INSERT dòng mới cùng family (hash mới, hạn mới, tối đa family_expires_at)
  COMMIT
  → trả { token, expires_at, refresh_token, refresh_expires_at }
```

**Vì sao `FOR UPDATE`:** hai tab cùng refresh một token là chuyện thật. Không khoá row thì cả
hai đều đọc thấy `rotated_at = NULL`, cùng xoay → sinh hai nhánh, lần refresh sau của một nhánh
bị coi là "reuse" oan và user bị đá. Khoá row khiến request thứ hai thấy token đã xoay.

**Vì sao token cũ không bị xoá:** giữ lại để biết nó "đã dùng" — đó chính là bằng chứng để phát
hiện reuse. Janitor chỉ xoá sau khi hết hạn/revoked quá 7 ngày.

### 2.4. Logout và đổi mật khẩu

- `POST /auth/logout { refresh_token }`: tìm family chứa token rồi thu hồi **mọi token còn sống**
  của family. Idempotent — token lạ vẫn trả 200 với `revoked: 0` (không cho phép dò token).
- `POST /auth/logout-all` (cần Bearer): thu hồi toàn bộ family của user — dùng khi nghi lộ token.
- Đổi mật khẩu: `PasswordChangedAt` đá access token như cũ; thêm `RevokeAllByUser` đá refresh token.

### 2.5. Vòng đời một token

```
login ──► RT1 (family F, 30d)
             │ refresh
             ▼
           RT1 [rotated] ──► RT2
                               │ refresh
                               ▼
                             RT2 [rotated] ──► RT3
                                                 │
      RT1 xuất hiện lại ──► REUSE ──► revoke cả F (RT3 chết theo)
```

## 3. API contract

### 3.1. Login (bổ sung field, không phá vỡ client cũ)

```json
{
  "token": "eyJhbGciOi...",
  "expires_at": "2026-10-23T10:00:00+07:00",
  "refresh_token": "8f3kQ2...",
  "refresh_expires_at": "2026-11-21T10:00:00+07:00",
  "user": { "...": "..." }
}
```

`token` giữ nguyên nghĩa (access token) nên FE cũ không phải sửa gì ngay.

### 3.2. Refresh

```http
POST /api/v1/auth/refresh
Content-Type: application/json

{ "refresh_token": "V9x1mP..." }
```

```json
{
  "token": "eyJhbGciOi...",
  "expires_at": "2026-10-22T10:15:00+07:00",
  "refresh_token": "new-opaque-token",
  "refresh_expires_at": "2026-11-21T10:00:00+07:00"
}
```

Mọi lỗi xác thực trả **cùng một** 401 `"phiên đăng nhập không hợp lệ hoặc đã hết hạn"` — không
phân biệt token không tồn tại / hết hạn / bị thu hồi / reuse, để người dò token không biết mình
đang ở bước nào.

### 3.3. Logout / Logout-all

```http
POST /api/v1/auth/logout          # public, body { "refresh_token": "..." }
POST /api/v1/auth/logout-all      # Bearer access token
```

Cả hai trả `{ "revoked": <số token bị thu hồi> }`.

## 4. Config và lộ trình hạ hạn access token

```json
"jwt": {
  "secret": "...",
  "expiry_minutes": 1440,
  "refresh_expiry_days": 30,
  "refresh_absolute_days": 90
}
```

- `refresh_expiry_days` mặc định 30, tối đa 365.
- `refresh_absolute_days` mặc định 90, không được nhỏ hơn `refresh_expiry_days`, tối đa 730.

**Quan trọng — đừng hạ `expiry_minutes` xuống 15 ngay:** FE hiện chỉ lưu `token` và chưa gọi
refresh. Hạ trước khi FE sẵn sàng = user bị đá ra sau 15 phút. Lộ trình:

1. Deploy BE (đã xong): login trả thêm refresh, endpoint refresh/logout sẵn sàng, access vẫn 24h.
2. FE triển khai refresh (xem 5.1).
3. Đổi `expiry_minutes` = 15, restart API.

## 5. Phía FE cần làm (khi bắt đầu dùng refresh)

### 5.1. Single-flight — bắt buộc

Vì mỗi refresh token chỉ dùng một lần, **hai request refresh song song với cùng token sẽ bị coi
là reuse và đăng xuất user**. FE phải đảm bảo:

- Trong một tab: một biến promise dùng chung, request thứ hai chờ request thứ nhất.
- Giữa các tab: dùng `BroadcastChannel` hoặc lock qua `localStorage` để chỉ một tab refresh.
  Đây là yêu cầu thiết kế, không phải "nice to have".
- Khi refresh trả 401 → xoá token, điều hướng về trang đăng nhập (không retry vô hạn).

### 5.2. Lưu token ở đâu

P0 chọn **body JSON** (không dùng cookie) để không phải đổi CORS/credentials và hợp FE SPA khác
domain. Hệ quả: refresh token nằm trong storage của FE, XSS vẫn lấy được. Nếu muốn chống XSS tốt
hơn, P1 chuyển refresh token sang cookie `HttpOnly; Secure; SameSite` (khi đó cần chống CSRF).

### 5.3. Retry sau refresh

Khi API trả 401 do access hết hạn: gọi refresh **một lần**, cập nhật cả hai token, rồi retry
request gốc. Không refresh cho lỗi 401 của `/auth/login` hay `/auth/refresh`.

## 6. Các quyết định và lý do

| Quyết định | Lý do | Đánh đổi |
|---|---|---|
| Refresh token opaque, không phải JWT | Server phải tra DB để thu hồi được; opaque đơn giản, không cần ký, không lộ claims | Mỗi lần refresh có 1 query (rất thưa, không ảnh hưởng) |
| Lưu SHA-256 thay vì token gốc | DB lộ cũng không dùng lại được; tra cứu bằng unique index | Không thể "xem lại" token của user (không cần) |
| Rotation mỗi lần dùng | Phát hiện token bị copy | Cần FE single-flight |
| Reuse → thu hồi cả family | Không biết ai là kẻ trộm, phải cắt cả hai | User thật có thể bị đăng xuất oan nếu FE refresh song song |
| Family + hạn tuyệt đối 90 ngày | Chặn token bị đánh cắp sống mãi; vẫn đủ tiện cho user thường | Phải login lại sau 90 ngày |
| Refresh/logout là endpoint public | Access hết hạn vẫn logout/refresh được; bảo vệ bằng chính refresh token | Cần rate limit ở P1 (hiện dựa vào 256-bit entropy) |
| Chưa kiểm tra session mỗi request | Giữ nguyên 1 query DB/request như cũ | Logout không huỷ access token ngay; trễ tối đa bằng hạn access |
| Trả 401 chung cho mọi lỗi | Không cho kẻ dò token biết token có tồn tại | Debug khó hơn — bù bằng log server |
| Không đổi `expiry_minutes` ngay | Tránh đá user khi FE chưa hỗ trợ refresh | Cửa sổ rủi ro 24h vẫn còn tới bước 3 |

## 8. Test

```powershell
go test ./src/common/utils -run TestNewOpaqueToken -v
go test ./src/controller/services -run "TestLogin|TestRefresh|TestLogout|TestDoiMatKhau" -v
go test ./src/infrastructure/repository -run TestRefreshTokenRepository -v
```

Đã phủ:

- Token sinh ngẫu nhiên, hash ổn định, không lưu token gốc.
- Login tạo đúng 1 row, hash khớp token trả client, hạn 30/90 ngày.
- Refresh xoay token, trả cặp mới, token mới không vượt hạn family.
- Reuse → 401 + thu hồi family (hash + lý do đúng).
- Token không tồn tại/hết hạn/bị thu hồi → 401.
- User bị khoá → 403 + thu hồi mọi token.
- Logout idempotent; đổi mật khẩu thu hồi mọi phiên.
- Repository thật (Postgres): rotate, reuse, revoke, token hết hạn, family hết hạn, janitor xoá cứng.

## 9. Chưa làm (P1) và điều kiện làm

1. **Huỷ access token ngay khi logout**: thêm claim `sid = family_id` và kiểm tra family chưa bị
   thu hồi mỗi request. Cần thêm 1 query/request (hoặc join vào query user hiện có) — chỉ đáng
   làm khi access TTL vẫn dài hoặc có yêu cầu bảo mật cao.
2. **Cookie `HttpOnly` cho refresh token**: khi FE và API cùng site; cần chống CSRF.
3. **Hạ access TTL xuống 15 phút**: sau khi FE single-flight xong.
4. **UI "thiết bị đang đăng nhập"**: đọc `user_agent`, `ip`, `created_at` theo `user_id`; cho
   phép thu hồi từng family. Dữ liệu đã có sẵn.
5. **Rate limit `/auth/refresh`**: hiện dựa vào entropy 256-bit; nếu cần chặn scan thì thêm
   limiter theo IP (lưu ý NAT văn phòng).
6. **Reuse grace window**: nếu thực tế có nhiều user mở nhiều tab và bị đăng xuất oan, cân nhắc
   cho phép dùng lại token cũ trong ~10 giây và trả lại đúng cặp token đã phát. Phức tạp, chỉ làm
   khi có số liệu thật.

## 10. Checklist khi deploy

- [ ] Chạy API một lần để `AutoMigrate` tạo bảng `refresh_tokens`.
- [ ] Chạy worker để job `purge-refresh-tokens` hoạt động (mỗi ngày).
- [ ] Theo dõi log `auth: refresh token bị dùng lại` — nếu xuất hiện thường xuyên, kiểm tra FE
      có refresh song song không.
- [ ] Không log token; log đã gắn `user_id`/`family_id`/`ip`.
- [ ] Sau khi FE xong: đổi `jwt.expiry_minutes = 15` và restart API.
